# VPN-кабинет

**Веб-кабинет VPN-сервиса: вход по почте или Telegram, подписки, покупка и смена региона — без приложения.**

![Live](https://img.shields.io/badge/live-utilio.cc-2ea44f)

</div>

> **Коротко.** У VPN-сервиса аккаунт жил только в Telegram: «аккаунт» — это `chat_id`.
> Человек без доступа к Telegram не мог ни войти, ни продлить подписку — а VPN нужен
> как раз там, где Telegram недоступен. Кабинет даёт второй вход по почте, не ломая
> Telegram, и связывает оба способа в один аккаунт.

**Ссылки:** [живое демо](https://utilio.cc) · [архитектура](docs/architecture.md) · [спека](docs/2026-10-17-cabinet-design.md)

## Проблема

Аккаунт в сервисе существовал только как Telegram-пользователь. Отсюда три
следствия, каждое из которых бьёт по деньгам:

- **Замкнутый круг.** Чтобы получить VPN, нужен VPN: в части сетей Telegram
  недоступен, а без Telegram нет доступа к аккаунту и оплате.
- **Нет двери для новых клиентов.** Регистрация требовала Telegram — канал,
  который часть аудитории не использует вовсе.
- **Состояние входа расходится.** Сессия в приложении и «сессия» в кабинете — разные
  таблицы; выход в браузере оставлял человека залогиненным в приложении.

Плюс отдельная опасность: любой вход «по второму способу» — классическое место
захвата аккаунта (pre-account hijacking), если привязка не требует подтверждения
владения.

## Что умеет

- **Вход по почте** — одноразовый код на адрес, с TTL и лимитами на подбор и отправку.
- **Вход по Telegram** — через бота: кабинет получает подтверждённый ботом `chat_id`,
  а не верит введённому.
- **Связывание способов входа** в любую сторону: Telegram к почтовому аккаунту и
  почту к Telegram-аккаунту. Новый способ — только после подтверждения владения им.
- **Отвязка с защитой** — нельзя остаться без единого способа входа.
- **Подписки** — список, срок, статус.
- **Покупка** — `/buy` → выбор серверов → оплата ЮKassa → `/buy/done`.
- **Смена региона** и **скачивание конфига** прямо из кабинета.
- **Правовые страницы** — условия и политика конфиденциальности как отдельные экраны.

## Стек

| Слой | Технологии |
|---|---|
| Backend | Python 3.11, FastAPI, Uvicorn |
| Шаблоны / UI | Jinja2, серверный HTML, CSS (`cabinet/static/cabinet.css`) |
| Внутренняя связь | HTTP к API бота на loopback, общий секрет в заголовке |
| Почта | SMTP или HTTP-API (Brevo), конфиг через env |
| Оплата | ЮKassa (создание платежа + вебхук) |
| Тесты | pytest, pytest-asyncio, мок-слой `tests/fakes.py` |
| CI | GitHub Actions: `ruff check`, `ruff format --check`, `pytest` |

## Как это устроено

```
браузер ──HTTPS──▶ nginx ──▶ cabinet (FastAPI, 127.0.0.1:8000)
                                  │  /internal/* + X-Internal-Secret
                                  ▼
                                 бот ──MySQL: accounts, users, orders, servers
                                  ▲
                    ЮKassa ──вебхук──┘  (bot пересылает событие в кабинет)
```

**Главное решение — граница.** Кабинет не ходит в базу напрямую. Репозиторий
публичный, и SQL со схемой таблиц авторизации в нём выставил бы внутреннее
устройство на вид. Вместо этого кабинет обращается к внутреннему роутеру бота
(`/internal/*`) на loopback с общим секретом в заголовке. Поэтому кабинет можно
переписать и развернуть, не задев данные бота.

Модули разделены по ответственности и работают против интерфейсов, а не против
конкретного клиента:

| Модуль | Роль |
|---|---|
| `cabinet/app.py` | HTTP-слой: роуты, cookie-сессия, сборка приложения через `build_app` |
| `cabinet/signin.py`, `auth_mail.py` | Вход: коды на почту, их выдача и проверка |
| `cabinet/linking.py` | Привязка и отвязка способов входа — единственное место, где аккаунт получает второй вход |
| `cabinet/sessions.py` | Сессии, принадлежащие `account_id`, а не `chat_id` |
| `cabinet/bot_client.py` | HTTP-клиент к боту и адаптеры `BotStore` / `BotSessionStore` |
| `cabinet/payments.py`, `pricing.py`, `subscriptions.py` | Покупка, цены, подписки |
| `cabinet/configs.py`, `pending_mail.py`, `mail_sender.py` | Конфиги, отложенные письма, отправка |
| `cabinet/render.py`, `theme.py`, `templates/` | Разметка экранов |

Сборка зависимостей — одна функция `build_app`, принимающая реализации
параметрами. Роуты не знают, живой под ними бот или подставной: в тестах
подставляются `FakeMailSender` и подставной бот, в бою — `BotStore` и живая почта.
Запуск без обязательных переменных окружения **отвергается** с ненулевым кодом
выхода, а не откатывается на подставные значения.

**Экраны** (по шаблонам в `cabinet/templates/`):

| Экран | Назначение |
|---|---|
| `login`, `login_waiting`, `login_telegram` | Вход по коду из письма или через Telegram-бота |
| `linking` | Привязка второго способа входа и отвязка |
| `subscriptions` | Действующие подписки и их срок |
| `buy`, `buy_servers`, `buy_pay`, `buy_confirm`, `buy_done` | Пошаговая покупка |
| `region` | Смена региона |
| `legal_terms`, `legal_privacy` | Условия и политика конфиденциальности |

**Поток покупки.** Человек выбирает тариф (`/buy`), затем серверы
(`/buy_servers`), подтверждает заказ (`/buy_confirm`) и уходит на оплату
(`/buy_pay`). ЮKassa присылает вебхук в бота, бот пересылает событие в кабинет,
и после успешной оплаты человек попадает на `/buy/done`. Заказ, его статус и
конфиг ведёт бот — кабинет только показывает и переспрашивает.

**Тестовый слой.** Мок-модуль `tests/fakes.py` общий для всех волн; поверх него
написаны сценарные тесты (`test_e2e_journey`, `test_login_*`, `test_linking_security`,
`test_purchase_*`, `test_payment_webhook`), тесты отказных состояний
(`test_bot_outage_screens`) и проверка, что все внутренние ссылки живые
(`test_all_links_resolve`). Маркер `live` отделяет сценарии, которым нужен
настоящий бэкенд.

## Инженерные находки

- **Граница «кабинет ↔ бот» снижает и риск, и связанность.** Секрет и адрес бота
  задаются только окружением (`BOT_BASE_URL`, `CABINET_INTERNAL_SECRET`) и никогда
  не хардкодятся; кабинет слушает `127.0.0.1`, наружу его выставляет nginx.
- **Привязка не проще входа.** Правило из спеки §3.3: новый способ входа
  подтверждается не слабее существующего. Telegram приходит подтверждённым ботом;
  почта — только после кода, отправленного на этот самый адрес. Занятое место не
  перезаписывается никогда.
- **Два уровня защиты от гонки при привязке.** Проверка «пусто ли место» есть и в
  модели (`can_link_telegram`), и в хранилище (`WHERE ... IS NULL`). Расхождение
  между «можно ли было» и «что получилось» ведёт к отказу, а не к тихой перезаписи.
- **Сессия принадлежит аккаунту, а не способу входа.** У человека, вошедшего по
  почте, `chat_id` пуст; сессия на `chat_id` ему недоступна вовсе. Одна таблица
  сессий бота означает, что выход в браузере гасит и приложение.
- **Коды на почту: хеш, TTL, лимиты, постоянное время сравнения.** В памяти лежит
  `sha256` кода, сравнение — `hmac.compare_digest`, проверка удаляет запись
  (одноразовость), число попыток и отправок ограничено.
- **Cookie: `HttpOnly` + `SameSite=Lax` + скользящий `Max-Age`.** `Lax` пропускает
  переход по ссылке из письма, но не отдаёт cookie сторонним POST; `Max-Age`
  выпускается заново при каждом заходе, иначе активного человека выбрасывало бы
  через TTL от первого входа (issue #53).
- **Отказ бота — по коду, а не по тексту.** Клиент различает `BotUnreachable`
  (сеть, таймаут — повторяемо) и `BotError` (осмысленный отказ — повторять
  бессмысленно и иногда вредно); ветвление идёт по `code` из единого формата ошибок.
- **CI пишет падения в аннотации, а не только в лог.** Скачать лог джобы может
  только администратор репозитория, а аннотации доступны через check-runs API —
  поэтому хвост `pytest` уходит в аннотацию, и отладка не идёт вслепую.

## Быстрый старт

```bash
git clone https://github.com/impossi8le/vpn-cabinet.git
cd vpn-cabinet
python -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -e ".[dev]"

cp .env.example .env                              # заполнить переменные (см. ниже)
python -m cabinet                                  # http://127.0.0.1:8000
```

Обязательные переменные окружения (значения — только в `.env`, не в репозитории):

| Переменная | Что задаёт |
|---|---|
| `BOT_BASE_URL` | Адрес внутреннего API бота |
| `CABINET_INTERNAL_SECRET` | Общий секрет в заголовке запросов к боту |
| `CABINET_PUBLIC_BASE` | Публичный адрес кабинета (ссылки в письмах) |
| `CABINET_PORT` | Порт прослушивания, по умолчанию `8000` |
| `MAIL_TRANSPORT`, `MAIL_FROM`, `MAIL_SMTP_*` / `MAIL_API_*` | Отправка писем |
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | Оплата |

Проверки — те же, что в CI:

```bash
ruff check .
ruff format --check .
pytest
```

Тесты по умолчанию идут против моков: ни один не ходит в сеть и не требует бота.
Живые сценарии помечены маркером `live` и по умолчанию не запускаются.

## Статус и ограничения

- **Работает на боевом сервисе:** https://utilio.cc. Приложение — systemd-юнит
  `cabinet-app`, внутренний API аккаунтов — `cabinet-api`.
- **Тестов много.** В репозитории 52 файла тестов и 620+ функций `def test_`;
  в README репозитория встречается цифра 667 — точное число зависит от
  параметризации и здесь не перепроверялось.
- **Тесты — против моков.** Живой бот и живая почта в CI не участвуют; маркер
  `live` существует, но по умолчанию выключен.
- **Хранилище кодов — в памяти процесса.** Это осознанный выбор: коды живут
  минуты и переживать перезапуск не обязаны. Перезапуск кабинета сбрасывает
  выданные, но ещё не использованные коды.
- **Лицензия не определена.** Открытый вопрос вынесен в `vpn-app-design`
  (`docs/README.md`), файла `LICENSE` в репозитории нет.
- **Публичной документации API нет.** Контракт с ботом описан в
  `docs/2026-10-17-backend-contract.md` для внутреннего использования.
