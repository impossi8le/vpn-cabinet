# Что нужно от бота: контракт внутреннего API

Дата: 2026-10-17. Статус: **ТЗ для бэкенда**. Владелец темы: этот документ.

Кабинет не ходит в базу (см. [замысел §3.4](2026-10-17-cabinet-design.md)):
он обращается к боту по внутреннему HTTP на loopback. Здесь описано, **что
именно должен уметь этот роутер**, чтобы кабинет заработал.

Документ существует отдельно от спеки намеренно: спека объясняет **почему так
устроен аккаунт**, а этот файл — **что реализовать**, с полями и кодами ошибок.
Реализация живёт в репозитории бота, там же и проверяется.

---

## 0. Общие правила

| Правило | Значение |
|---|---|
| Транспорт | HTTP по loopback. Наружу роутер не выставляется |
| Формат | JSON, UTF-8 |
| Префикс | `/internal` |
| Аутентификация | заголовок `X-Internal-Secret`, общий секрет кабинета и бота |
| Отказ без секрета | `401` с `{"error": {"code": "unauthorized"}}` |
| Формат ошибки | `{"error": {"code", "message", "retryable"}}` — тот же, что у `client_api_svc.py` |
| Логирование | никогда не логировать секрет, коды подтверждения и содержимое `.ovpn` |

Секрет сравнивается устойчиво к таймингу (`hmac.compare_digest`), как это уже
сделано в `utils/client_auth_db.py` для секретов входа.

`code` присутствует **всегда** — кабинет ветвится по коду, а не по тексту. Это
то же требование, что клиент предъявляет к публичному API: голый статус без
кода не отличим от неожиданного ответа.

## 1. Аккаунты

### `GET /internal/accounts/by-chat-id?chat_id=<int>`

Найти аккаунт по Telegram id.

```json
{"account": {"id": 7, "chat_id": 123456789, "mail": null, "mail_verified_at": null}}
```

Не найден → `404` с `code: account_not_found`. Кабинет по этому коду решает
«завести аккаунт», а по недоступности — «повторить».

### `GET /internal/accounts/by-mail?mail=<string>`

Симметрично поиску по `chat_id`. Адрес сравнивается без учёта регистра и
пробелов по краям: `User@Example.COM` и `user@example.com` — один аккаунт.

### `POST /internal/accounts`

Создать аккаунт. Тело — одно из двух:

```json
{"chat_id": 123456789}
{"mail": "user@example.com", "mail_verified_at": "2026-10-17T12:00:00Z"}
```

Ответ `201` — созданный аккаунт в том же виде.

**`chat_id` принимается только от доверенного вызывающего.** Роутер вызывается
только с loopback и только с секретом, поэтому подтверждение личности остаётся
на стороне бота: кабинет узнаёт `chat_id` лишь из подтверждённого флоу входа.
Это граница, которую нельзя переносить в кабинет.

`409` с `code: chat_id_taken` или `code: mail_taken` — значение уже занято.
**Никогда** не перезаписывать: занятый `chat_id` означает, что аккаунт уже
привязан, и тихая перезапись была бы угоном.

`400` с `code: mail_not_verified` — `mail` без `mail_verified_at`.

### `POST /internal/accounts/{id}/link-telegram`

Привязать Telegram к аккаунту.

```json
{"chat_id": 123456789}
```

**Обязательное поведение:**

```sql
UPDATE accounts SET chat_id = ? WHERE id = ? AND chat_id IS NULL
```

Ответ `{"ok": true}` при `rowcount = 1`. При `rowcount = 0` — `409` с
`code: chat_id_taken`. Условие `AND chat_id IS NULL` не украшение: именно оно
закрывает перезапись как класс, независимо от того, что успел проверить
кабинет между чтением и записью.

> **Поправка от 2026-10-23 (сверено с кодом бота).** Живой роутер отдаёт
> `{"ok": true, "account": {…}}` — на одно поле больше, чем описано выше.
> `account` там потому, что кабинет читает состояние **после** записи и показывает
> то, что сохранено, а не то, что просил. Описанный выше минимум (`ok`) остался:
> кабинет читает `account`, а `ok` держится для совместимости с этим текстом.
> См. `services/cabinet_api_svc.py`, обработчик `link-telegram`.


Если `chat_id` уже занят **другим** аккаунтом — `409`, и это отдельный код
`code: chat_id_taken`, чтобы кабинет мог предложить войти тем способом.

### `POST /internal/accounts/{id}/link-mail`

Привязать почту. Тело — `{"mail": ..., "mail_verified_at": ...}`.
Поведение симметрично: `AND mail IS NULL`, `409 code: mail_taken`.
`mail_verified_at` обязателен, `400 code: mail_not_verified` без него.

### `POST /internal/accounts/{id}/unlink-telegram` и `/unlink-mail`

Отвязать способ входа.

**Обязательное поведение:** отказ `409` с `code: last_login_method`, если после
отвязки у аккаунта не остаётся ни одного способа входа. Аккаунт без способов
недоступен навсегда — это не ошибка пользователя, которую можно пережить.

### `GET /internal/accounts/{id}`

Прочитать один аккаунт. Нужен кабинету, чтобы показать, что привязано.

## 2. Подписки

### `GET /internal/accounts/{id}/subscriptions`

```json
{"subscriptions": [
  {"id": "nl-ams-1", "name": "Нидерланды · Амстердам", "status": "active",
   "end_date": "2026-12-01T00:00:00Z", "location": "Амстердам"}
]}
```

Поля и форма — как элементы `configs` в публичном контракте
(`vpn-app-design/docs/architecture/2026-10-02-api-contract.md` §3). Кабинет
показывает пользователю то же, что приложение, поэтому форма должна совпадать.

**Пустой `subscriptions` — валидный ответ, не ошибка.** Состояние «подписок
нет» существует и должно отображаться.

`status` ∈ `active` | `trial` | `expired` | `blocked`. Незнакомое значение
кабинет трактует как «доступа нет» — но это не повод присылать произвольные
строки: закрытый набор лучше.

### Решение по `status` принимает бот, но не слепо

Кабинет сравнивает `end_date` с текущим временем и применяет правило: **дата
отнимает доступ, но не возвращает**. `active` с прошедшим сроком доступа не
даёт, `expired` с будущим сроком — тоже.

Это дублирование намеренное: оно защищает от того, что бот забудет обновить
статус. Но присылать статус, противоречащий дате, всё равно не следует.

## 3. Конфиги

### `GET /internal/accounts/{id}/configs/{config_id}`

Содержимое `.ovpn`.

**Ответ `200`:** сырое содержимое, `Content-Type: application/x-openvpn-profile`,
заголовки `X-Config-Version` и `X-Config-Hash: sha256:...` — как в публичном
контракте §4.

**Отказы:**

| HTTP | code | Когда |
|---|---|---|
| `403` | `config_revoked` | конфиг отозван |
| `402` | `subscription_expired` | подписка истекла |
| `404` | `config_not_found` | нет такого конфига или он чужой |
| `410` | `config_retired` | конфиг снят на сервере |

**«Нет конфига» и «чужой конфиг» — один и тот же ответ.** Иначе перебором
`config_id` выяснялось бы, у кого что есть.

Конфиг отдаётся только активной подписке. Проверка — на стороне бота: кабинет
не должен решать это сам, иначе появится второй источник правды о доступе.

## 4. Сессии

### `POST /internal/sessions/for-account`

Выдать сессию кабинета по `account_id`.

```json
{"account_id": 7}
```

**Требование, которое меняет существующую схему.** Сейчас `client_sessions`
хранит `chat_id NOT NULL`, и сессия не может принадлежать аккаунту без
Telegram. Кабинету это нужно: главный случай — человек, зарегистрировавшийся
по почте и Telegram не привязавший.

Решение на выбор бэкенда, оба приемлемы:

1. Добавить в `client_sessions` колонку `account_id` и перейти на неё как на
   владельца сессии, оставив `chat_id` для совместимости с Android-клиентом;
2. Завести отдельную таблицу сессий кабинета.

**Первый вариант предпочтителен:** одна таблица сессий на обе точки входа
означает, что вход в кабинете и вход в приложении видят одно состояние, и
разлогин действует везде. Две таблицы разойдутся — вопрос времени.

Ответ:

```json
{"token": "...", "expires_at": "2026-11-16T12:00:00Z", "account_id": 7,
 "created_at": "2026-10-17T12:00:00Z"}
```

**`created_at` обязателен (issue #53).** Срок сессии продлевается при каждом
заходе, но у продления есть потолок, отсчитанный от момента появления сессии.
Без `created_at` кабинет не отличает продлённую сессию от только что выданной,
и тогда токен, которым пользуются хотя бы раз в срок, живёт бесконечно —
обещание «украденный токен перестаёт работать сам» остаётся верным только для
токена, которым не пользуются.

Обновление времени последней активности — на стороне бота; `created_at` этим
обновлением **не** сдвигается.

### `GET /internal/sessions/current`

Проверить сессию по токену из заголовка `Authorization: Bearer <token>`.

```json
{"account_id": 7, "chat_id": 123456789, "mail": "user@example.com",
 "expires_at": "2026-11-16T12:00:00Z"}
```

`401` с `code: unauthorized` — токен неизвестен, истёк или отозван. Обновление
времени последней активности — на стороне бота.

### `POST /internal/sessions/revoke`

Выход. Тело — `{"token": ...}`. Идемпотентно: повторный выход не ошибка.

## 4а. Отвязка: что происходит с конфигами

Требование владельца: перед отвязкой спросить, **что отвязываем** и **какой
аккаунт остаётся основным** — он и будет идентификатором для конфигов.
И объяснить последствие.

### Почему это нужно объяснять, а не делать молча

Конфиги в системе привязаны к `chat_id` (см. [покупку §3](2026-10-17-purchase-flow-design.md)).
Почта сама по себе конфигов не имеет — она лишь способ входа в аккаунт.
Значит отвязка **не удаляет конфиги**, а меняет то, **по какому ключу они
достаются**. Человек, который думает, что отвязка почты «убирает» его
подписки, будет неприятно удивлён или наоборот — испугается зря.

### Что показывать

**Отвязка почты** (остаётся Telegram):

> Отвязываем почту. Все конфиги, которые сейчас на почте, привязываются к
> вашему Telegram и будут доступны **только по нему**. Войти по почте больше
> не получится — вход останется через Telegram.

**Отвязка Telegram** (остаётся почта):

> Отвязываем Telegram. Все конфиги, которые сейчас на Telegram, привязываются
> к вашей почте и будут доступны **только по ней**. Войти через Telegram
> больше не получится — вход останется по почте.

Формулировка «конфиги **привязываются** к оставшемуся способу» выбрана
намеренно: они не теряются и не копируются — меняется ключ, по которому
выдаются. Обещать «останутся у вас» было бы неполной правдой: останутся, но
достать их можно будет только оставшимся способом.

### Что требуется от бота

1. **Отвязка перепривязывает конфиги**, а не оставляет их ссылаться на
   отвязанный ключ. Если конфиг остался привязан к `chat_id`, а Telegram
   отвязан, — конфиг перестанет находиться, и это потеря доступа, а не
   безопасное удаление.
2. **Перед отвязкой бот сообщает, что перейдёт.** Кабинет показывает
   последствие из ответа бота, а не придумывает текст сам: сколько конфигов
   затронуто — знает только бот.

```
GET  /internal/accounts/{id}/unlink-preview?method=mail|telegram
     → {"configs_affected": 3, "remaining_method": "telegram"}
```

3. **Отвязка последнего способа запрещена** — уже в контракте (§1,
   `code: last_login_method`). Здесь это становится ещё важнее: отвязать
   единственный способ значит не просто потерять вход, а потерять и конфиги.

## 5. Вход по Telegram: чего делать НЕ нужно

Флоу входа уже реализован: `POST /auth/link` → подтверждение в боте →
`POST /auth/poll` (§1–§2 публичного контракта, защита от login-CSRF в §2.1).

Кабинет **переиспользует его как есть**. Новых эндпоинтов для входа не
требуется; требуется одно изменение в боте:

**После успешного `/auth/poll` бот должен создать или найти аккаунт** для
подтверждённого `chat_id` и вернуть `account_id` рядом с `session_token`:

```json
{"status": "confirmed", "session_token": "...", "expires_at": "...",
 "chat_id": 123456789, "account_id": 7}
```

Логика: аккаунт ищется по `chat_id`; не найден — создаётся (при подтверждённом
`chat_id` это безопасно: подтверждение уже произошло). Поле `account_id`
добавляется рядом с существующими, старый Android-клиент его не читает и
продолжает работать.

**Границы регистрации против входа.** Кабинет различает два случая по времени:
подтверждение в течение окна после `/auth/link` — регистрация, позже — вход.
Это нужно для инварианта «привязывать `chat_id` можно только пока аккаунт
новый» (§3.3 спеки). Если бот может отдать признак сам — лучше отдавать его
полем, чем давать кабинету считать по часам.

### 5.1. Режим привязки: тот же флоу, но без создания аккаунта

**Зачем.** Вход через Telegram работает, а привязки не было вовсе: у почтового
аккаунта кнопка «Привязать Telegram» показывала текст «откройте бота» и не делала
ничего — бот не знал, к какому аккаунту кабинета привязывать. Из-за этого
замыкался круг: подписки и конфиги живут на `chat_id`, аккаунту без Telegram
выдать нечего, экран оплаты отправляет привязывать Telegram, а привязка не
работает (issue #65).

**Почему нельзя переиспользовать вход целиком.** При входе `poll` создаёт аккаунт
для подтверждённого `chat_id`. При привязке это ломает саму операцию: свежий
Telegram **занимает новым аккаунтом** то самое место, которое кабинет собирался
заполнить, и привязка конфликтует сама с собой.

**Что нужно от бота** — режим у того же флоу, а не второй флоу:

- `POST /auth/link` принимает необязательное `mode`: `login` (по умолчанию) или
  `link`; неизвестное значение — отказ. Режим запоминается **в операции** и
  определяет ссылку на бота: `?start=login_<код>` или `?start=link_<код>`;
- подтверждение в боте в режиме привязки говорит человеку, что привязывает
  Telegram к аккаунту кабинета (а не «входит»), и отдаёт тот же `device_nonce`;
- `POST /auth/poll` при режиме `link` гасит операцию так же атомарно, но
  возвращает **только** `{"status": "confirmed", "chat_id": <подтверждённый>}`:
  ни `session_token`, ни `account_id`, и **никакого создания аккаунта**.

**Что делает кабинет.** Тем же опросом получает подтверждённый `chat_id` и
привязывает его **в пустое место** своего аккаунта (`POST
/internal/accounts/{id}/link-telegram`, §1). Место занято — бот отвечает
`chat_id_taken`, и кабинет говорит человеку прямо: «Этот Telegram уже привязан к
другому аккаунту». Перезапись занятого значения запрещена в SQL, а не только на
экране.

**Чего делать нельзя.** Подставлять `chat_id` из формы или адреса — он приходит
только из ответа бота, подтвердившего человека в Telegram (§3.3 спеки).

### 5.2. Ссылка возврата: вход одним нажатием из сообщения бота

**Зачем.** Бот присылает человеку только код: шесть цифр нужно скопировать,
вернуться в кабинет и ввести их. Владелец попросил, чтобы в сообщении была
**готовая ссылка**, по которой человек попадает в кабинет уже вошедшим, — а код
остаётся вторым, ручным путём (issue #52).

**Что нужно от бота.**

- `POST /auth/link` принимает необязательное поле `return_base` — **полный адрес
  роута возврата кабинета**, без параметров (например
  `https://<кабинет>/login/telegram/return`). Свои пути знает кабинет, поэтому
  адрес целиком приходит от него, а бот лишь дописывает параметры.
- В сообщении с кодом бот добавляет ссылку
  `{return_base}?public_code=<код челленджа>&nonce=<тот же device_nonce>`, то
  есть тот же код, который человек ввёл бы руками.
- `return_base` не передан (запрос Android-клиента) — сообщение остаётся
  **прежним**, только код: у клиента свой флоу, и менять его нельзя.
- Операция гасится первым успешным использованием — и по коду, и по ссылке, — а
  срок её жизни остаётся прежним.

**Что делает кабинет.** Роут `GET /login/telegram/return` берёт `public_code`,
находит у себя начатый челлендж (секрет живёт в памяти процесса), опрашивает бот
с `nonce` и на `confirmed` выдаёт сессию **тем же путём**, что экран ввода кода.
Личность по-прежнему называет только бот: `account_id` из ответа опроса.

**Почему ссылка — не послабление.** `nonce` в адресе — предъявительский токен:
кто прочитал сообщение, тот и войдёт. Поэтому одноразовость держит бот (операцию
гасит первый успех), срок короткий, а кабинет **не показывает этот адрес
дальше**: после успеха сразу уводит на подписки, запрещает кеширование ответа и
передачу адреса через `Referer`. Ввод кода руками работает наравне — второй путь
не заменяет первый.

## 6. Бесплатные 30 дней: что менять в боте

Требование владельца: **кнопка «30 дней бесплатно» в кабинете, но триал
доступен только после привязки Telegram, и повторная выдача блокируется
отдельно по `chat_id` и отдельно по почте.**

### Как триал устроен сейчас

В боте триал — это обычная строка в `users` с `is_trial = 1`. Проверка
«уже брал» — `has_used_trial_subscription(chat_id)`, и она смотрит **только
`chat_id`**:

```sql
SELECT COUNT(*) FROM users WHERE chat_id = %s AND is_trial = TRUE
```

### Отсюда три следствия для бота

**1. Триал без Telegram невозможен по устройству схемы.** `users.chat_id`
— ключ, по которому выдаётся и проверяется триал. Аккаунт, заведённый по
почте (`chat_id IS NULL`), триал получить не может. Это не ограничение,
которое надо обойти: триал без Telegram означал бы выдачу конфига в
`users` без владельца, к которому его потом привязать.

Поэтому в кабинете кнопка «30 дней бесплатно» **требует привязки Telegram**
и объясняет, почему: конфиг должен быть к чему-то привязан, иначе его
нельзя ни отозвать, ни продлить.

**2. Блокировка повторной выдачи нужна по обоим ключам, отдельно.**
Сейчас проверка одна — по `chat_id`. Этого мало: два разных `chat_id`,
у одного из которых привязана почта, а у другого нет, при нынешней проверке
не связаны, и почта не мешает взять триал дважды.

Нужна проверка **по двум осям независимо**:

| Ось | Что проверяет | Зачем |
|---|---|---|
| `chat_id` | брал ли триал этот Telegram | в боте уже есть |
| `mail` | брал ли триал аккаунт с этой почтой | **новое** |

Формулировка владельца: «заблокируют повторную выдачу по `chat_id` и почте
**по отдельности**». То есть блокировка по `chat_id` и блокировка по почте
работают независимо, и каждая закрывает свой путь повторного получения.

Практически: аккаунт, который уже брал триал через Telegram, не получит
второй, привязав почту. И наоборот — аккаунт, бравший триал с этой почтой,
не получит второй, даже если у него появился новый `chat_id`.

**3. Учёт триала должен пережить привязку.** Триал, взятый до привязки
почты, обязан считаться по почте тоже — иначе привязка почты обнуляла бы
историю. Значит, проверка по `mail` смотрит историю аккаунта, а не только
текущее состояние строки.

### Что добавить в контракт

```
GET  /internal/accounts/{id}/trial-eligibility
     → {"eligible": false, "reason": "trial_used_by_chat_id" | "trial_used_by_mail" | "telegram_required"}
```

Кабинет по `reason` показывает **разный текст**: «вы уже брали бесплатный
доступ» и «чтобы взять бесплатный доступ, привяжите Telegram» — это разные
ситуации, и человеку нужно разное действие.

Проверка выполняется **на стороне бота**, а не кабинета: решение о выдаче
триала — это решение о доступе, и второй источник правды о нём приведёт
к выдаче двух триалов одному человеку.

## 7. Чего в этом контракте нет и почему

- **Почты.** Отправка кода подтверждения живёт в кабинете: домен и транспорт
  не касаются бота. Бот получает уже подтверждённый адрес и отметку времени.
- **Платежей.** Оплата — следующий этап (§2 спеки, решение 8). Внутренние
  эндпоинты для неё появятся отдельно, вместе с миграцией
  `pending_payments.chat_id NOT NULL`.
- **Правки `users`, `referrals`, `pending_payments`.** Легаси-таблицы
  продолжают жить на `chat_id`; аккаунт с ними связывается через свой
  `chat_id`. Менять их на этом этапе не нужно.
