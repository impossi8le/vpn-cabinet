# Личный кабинет VPN: замысел

Дата: 2026-10-17. Статус: **в работе** — логика реализована (волны W0–W4),
интерфейс и живой бэкенд впереди. Владелец темы: этот документ.

Область: **архитектура ЛК** — модель аккаунта, способы входа, связывание
почты и Telegram, границы сервиса. Разбивка по заданиям — в
[плане](plans/2026-10-17-cabinet-implementation.md).

---

## 1. Задача

Дать пользователю веб-кабинет, куда он входит **по почте или по Telegram — на
выбор**, и где видит свои подписки и может скачать конфиги.

Сегодня аккаунт существует только в Telegram: «аккаунт» — это `chat_id`. У
человека, у которого нет доступа к Telegram, доступа к своему аккаунту нет
вообще. Это особенно остро для VPN-сервиса: **чтобы получить VPN, нужен VPN** —
в части сетей Telegram недоступен, и получается замкнутый круг.

Главное требование: **вход по почте должен быть полностью самостоятельным**.
Привязка Telegram — удобство, которое предлагается, но никогда не требуется.

## 2. Принятые решения

| # | Решение |
|---|---|
| 1 | Почта — основной способ входа, Telegram — дополнительный |
| 2 | Регистрация и вход по почте — **кодом на почту**, без пароля на старте |
| 3 | Вход по Telegram — **существующий флоу через бота** (`/auth/link` + `/auth/poll`), новый виджет не заводим |
| 4 | Аккаунт — **отдельная сущность** `accounts` с суррогатным id; `chat_id` и `mail` — атрибуты |
| 5 | Связывание **всегда требует подтверждения владением** тем, что привязывается |
| 6 | Сайт **не трогает MySQL** — ходит в бота по внутреннему HTTP |
| 7 | Разработка — **от тестов**, на mock-данных, до подключения живого бэкенда |
| 8 | Этап 1 — вход, подписки, конфиги. Оплата и поддержка — следующие этапы |

## 3. Почему такие решения

### 3.1 Почему отдельная таблица `accounts`

Вариант «прикрутить почту к `chat_id`» не работает для главного случая —
человека без Telegram: у него нет `chat_id`, и строку в `users` создать не к
чему привязать.

Разделение «аккаунт» и «способ входа» — это то, что рекомендуют Google
Identity Platform и WorkOS: один внутренний идентификатор, к которому
привязано несколько способов аутентификации. Плюсы здесь конкретные:

- **Стабильный id.** Не зависит ни от Telegram, ни от почты — их можно менять.
- **Готовность к другим способам.** Завтра добавить вход по телефону — это
  новая строка в `account_identities`, а не переделка схемы.
- **Существующие `chat_id` бэкфиллятся одной миграцией**, легаси-таблицы не
  трогаются: `users`, `pending_payments` и прочие продолжают жить на `chat_id`.

### 3.2 Почему вход по почте — кодом, а не паролем

Код на почту требует меньше кода и меньше рисков: нет восстановления пароля,
нет хранения хешей, нет политик сложности. Для сервиса, где аккаунт нужен
редко (посмотреть срок подписки, скачать конфиг), это честнее пароля, который
пользователь всё равно переиспользует.

Пароль как **второй** способ входа внутри кабинета добавить недорого — но
только после того, как заработает основное.

### 3.3 Почему связывание требует подтверждения

Это самая опасная часть, и класс ошибки здесь известен и свеж. CVE-2026-53516
(Better Auth) и nOAuth (Microsoft, 2023) — одна и та же ошибка: сервис
авто-связывает аккаунты, доверяя **заявлению провайдера** (`email_verified:
true`), не проверив, подтверждена ли **локальная запись**.

Атака: злоумышленник заранее регистрирует на сервисе чужой email. Жертва
потом входит через Telegram — и её личность прилипает к записи
злоумышленника, который сохраняет свой доступ.

Отсюда правило, которое в этой системе обязательно:

> **Привязка нового способа входа никогда не должна быть проще, чем вход
> существующими.**

Что это значит по шагам:

- `chat_id` присваивается **только** после подтверждения человеком в Telegram.
  Никогда — по заявленному в браузере «я такой-то».
- `mail` не может существовать без `mail_verified_at`.
- Авто-соединение с существующим `chat_id` разрешено **только** при
  `chat_id IS NULL` — то есть для нового аккаунта, а не для перепривязки.
  Технически это `UPDATE ... WHERE id = ? AND chat_id IS NULL`: если кто-то
  успел занять, `rowcount = 0`, и мы показываем ошибку вместо тихой перезаписи.
- Соединение запрещено, если `chat_id` попал в систему через **вход**, а не
  через регистрацию (разрыв с момента запроса больше окна регистрации).

### 3.4 Почему кабинет ходит в бота, а не в MySQL

Репозиторий кабинета **публичный**. Прямой доступ к БД означал бы, что в
открытом виде лежат SQL-запросы и схема таблиц авторизации. Это не секрет в
смысле уязвимости, но это детали внутреннего устройства, которым не место в
публичном репо — ровно та дисциплина, что уже действует в проекте для `.ovpn`
и логов.

Плюс два практических следствия: работа с сессиями и БД остаётся в одном месте
(в боте, рядом с `client_api_svc.py`), и не появляется второй копии логики
аутентификации, которая неизбежно разойдётся.

Граница — внутренний HTTP на `127.0.0.1` с общим секретом. Наружу этот роутер
не выставлен.

## 4. Модель данных

Одна строка = один человек.

```
accounts
  id                 BIGINT PK AUTO_INCREMENT   -- стабильный id аккаунта
  chat_id            BIGINT NULL UNIQUE          -- Telegram ID; NULL, пока не привязан
  mail               VARCHAR(255) NULL UNIQUE    -- почта; NULL, если не привязана
  mail_verified_at   DATETIME NULL               -- обязателен, если mail не NULL
  created_at         DATETIME NOT NULL
  updated_at         DATETIME NOT NULL
  last_login_at      DATETIME NULL
  blocked            TINYINT NOT NULL DEFAULT 0  -- блокировка аккаунта
```

Инварианты (проверяются кодом и тестами, не только схемой):

1. `chat_id` присваивается только после подтверждения в Telegram.
2. `mail` не может быть заполнен без `mail_verified_at`.
3. Смена `chat_id` — только на `NULL` (одноразовая привязка), через
   `WHERE id = ? AND chat_id IS NULL`.
4. Смена `mail` разрешена после подтверждения нового адреса; старый адрес
   освобождается.

**Бэкфилл.** Одна миграция заводит аккаунты для всех существующих
`chat_id` из `users`, чтобы старые пользователи вошли и сразу увидели свои
подписки:

```sql
INSERT INTO accounts (chat_id, created_at, updated_at)
SELECT DISTINCT u.chat_id, NOW(), NOW()
FROM users u
WHERE u.chat_id IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM accounts a WHERE a.chat_id = u.chat_id);
```

`users.chat_id` — nullable и **не** UNIQUE, поэтому `DISTINCT` обязателен.
Легаси-таблицы не меняются.

### Что будет на этапе 2 (оплата)

`pending_payments.chat_id`, `referrals.chat_id`, `user_analytics.chat_id` —
`NOT NULL`. Аккаунт без Telegram не сможет там отметиться. Это осознанно
отложено: на этапе 1 оплаты нет, email-аккаунты пустые, и миграция не нужна.
Модель к ней готова: у аккаунта есть суррогатный `id`.

## 5. Способы входа

| Ситуация | Что происходит |
|---|---|
| **Регистрация по email** | email → код на почту → `accounts(mail, chat_id = NULL)` → предложение привязать Telegram (**необязательное**) |
| **Вход по email** | email → код → сессия |
| **Вход по Telegram** | существующий `/auth/link` + `/auth/poll` → `chat_id` → находим или создаём `accounts(chat_id)` → сессия |
| **Привязка Telegram к email-аккаунту** | из кабинета → флоу бота → `UPDATE ... WHERE id = ? AND chat_id IS NULL` |
| **Привязка email к Telegram-аккаунту** | из кабинета → код на почту → `UPDATE ... WHERE id = ? AND mail IS NULL` |
| **Коллизия** | `chat_id`/`mail` занят другим аккаунтом → честная ошибка и предложение войти тем способом. **Никогда** не перезаписываем |

Сессии уже не зависят от способа входа: `client_sessions` хранит только
`chat_id` и токен. Кабинет ссылается на `account_id`, а `chat_id` из него
достаётся для запросов к существующему API.

## 6. Компоненты

| Модуль | Что делает | От чего зависит |
|---|---|---|
| `cabinet_api` | HTTP-эндпоинты кабинета, сессии, рендер страниц | `bot_client`, `render` |
| `bot_client` | Внутренний клиент к боту (`/internal/*`) | HTTP на 127.0.0.1 |
| `auth_mail` | Коды на почту: выдача, проверка, TTL, лимиты | `mail_sender` |
| `mail_sender` | Отправка письма — одна функция, разные транспорты | SMTP или API-сервис |
| `accounts` | Модель аккаунта и инварианты §4 | `bot_client` |

Со стороны бота (приватный репозиторий) добавляется роутер `/internal/*`:
аккаунты, поиск по `chat_id`/`mail`, подписки, сессии. Он работает только с
`127.0.0.1` и требует общий секрет.

## 7. Дизайн-система

Кабинет повторяет оформление Android-клиента: это тот же продукт, и человек,
пришедший из приложения на сайт, не должен видеть другой сервис. Источник —
`android/core/ui/src/main/kotlin/.../Tokens.kt` и `docs/design/mockup.html`
в репозитории `vpn-app-design`; там же готовые CSS-токены.

### Тема одна — тёмная

Светлая тема в клиенте отсутствует намеренно (решение UX-ревью, не упрощение).
Добавлять её в кабинет «как улучшение» нельзя без новой причины.

| Токен | Значение | Роль |
|---|---|---|
| `Void` | `#0A0C10` | фон |
| `Carbon` | `#12151B` | карточка |
| `Obsidian` | `#1A1E26` | приподнятая поверхность |
| `Hairline` | `#262B34` | граница |
| `Edge` | `#5A6472` | заметная граница |
| `TextSecondary` | `#8B95A3` | вторичный текст |
| `Mist` | `#AAB4C2` | текст между вторичным и основным |
| `Bone` | `#E8ECF2` | основной текст |

| `Green` | `#3DDC97` | подтверждённая защита |

| `Red` | `#FF5F6D` | реальная опасность |

Радиусы: карточка 14, кнопка 12, малое 8.

### Семантика цвета — несущее правило

За каждым цветом закреплён один смысл, и нарушать это нельзя:

- **Зелёный — только подтверждённая защита.** Не «подключено», не «туннель
  поднят», не «успешно сохранено». Ложный зелёный на экране проверки был
  главным дефектом, найденным на ревью макета клиента.
- **Янтарный — только идущий процесс.** Подключение, проверка кода, отправка
  письма. Больше нигде.
- **Красный — только реальная опасность.** Не «ошибка ввода», не «нет сети»,
  не «подписка истекла»: это состояния, а не опасность.
- **Своего брендового цвета нет.** Основная кнопка белая (`Bone`), `Ice`
  служит исключительно для выделения и фокуса.

Для кабинета это значит конкретное: **«подписка активна» — не зелёная**, там
нет замера защиты. Зелёный в кабинете уместен ровно в одном месте — если
пользователь пришёл с работающего туннеля и мы показываем подтверждённое
состояние, а не предполагаемое.

## 8. Что НЕ делаем

- **Не заводим Telegram Login Widget** — существующий флоу через бота уже
  реализован и защищён от login-CSRF (§2.1 контракта). Второй путь входа
  пришлось бы сводить в тот же аккаунт, это лишний риск ради одного клика.
- **Не переносим оплату** на этапе 1. Платёжный поток с вебхуками и
  идемпотентной доставкой трогать нельзя, пока кабинет не проверен вживую.
- **Не трогаем легаси-таблицы.** `mail_accounts` остаётся как есть: в ней
  данные пользователей, удаление необратимо.
- **Не делаем смену способа входа «тихой»** — любая привязка и отвязка
  оставляет запись в логе аудита.
- **Не даём отвязать последний способ входа** — аккаунт без способов входа
  недоступен навсегда.
