# Архитектура: карта связей, адреса и данные

Дата: 2026-10-24. Это **карта**, а не замысел: она описывает то, что в коде, и
отвечает на вопросы «какие адреса», «какие данные», «как связаны экраны».
**Замысел** и причины решений живут в [спеке кабинета](2026-10-17-cabinet-design.md)
и [спеке покупки](2026-10-17-purchase-flow-design.md) — здесь на них ссылаются,
а не пересказывают. Прав код: если документ расходится с ним, правится документ.

---

## 1. Участники и связи

```
        человек в браузере
                │ HTTPS
                ▼
   ┌──────────────────────────┐
   │  nginx (публичный вход)  │   вход  → кабинет:8008
   └───────────┬──────────────┘   /payments/* закрыт снаружи
               ▼
   ┌──────────────────────────┐
   │  КАБИНЕТ (FastAPI)       │   свой интерфейс, свои сессии,
   │  шаблоны, письма         │   своя интеграция оплаты
   └───┬──────────────────┬───┘
       │ /internal/*      │ /api/v1/auth/*   (публичный)
       │ + X-Internal-    │ вход по Telegram
       │   Secret         │
       ▼                  ▼
   ┌───────────────────────────────────────┐
   │  БОТ                                  │
   │  • внутренний API кабинета            │
   │  • публичный клиентский API           │
   │  • платёжный сервис ← уведомления ЮKassa
   │  • БД (MySQL): accounts, users,       │
   │    cabinet_orders, servers, …         │
   └───────┬───────────────────────────────┘
           │ генерация конфигов
           ▼
   бэкенд генерации (внешний по отношению к обоим)

   ЮKassa ──уведомление──▶ платёжный сервис бота ──пересылка──▶ кабинет
      ▲                                                         │
      └──────────── создание платежа и перезапрос ──────────────┘
```

**Правило границы:** кабинет **не трогает MySQL**. Всё, что ему нужно из данных,
он спрашивает у бота по HTTP с общим секретом. Поэтому кабинет можно переписать
и развернуть, не задев данные бота, а SQL со схемой авторизации не попадает в
публичный репозиторий.

## 2. Адреса кабинета (свои)

Экраны возвращают HTML; действия — редирект (303) либо тот же экран с текстом.
Авторизация — cookie `cabinet_session`, `HttpOnly`, `SameSite=Lax`, без `Secure`
(TLS снимается на прокси, поэтому признак ставит схема запроса).

### Вход

| Метод и адрес | Принимает | Что делает |
|---|---|---|
| `GET /` | — | уводит на `/subscriptions` |
| `GET /login` | `?mail=` | форма входа: почта **или** Telegram |
| `POST /login` | форма: `mail` | шлёт код; отказ приходит cookie и виден на `GET /login` |
| `GET /login/waiting` | `?mail=` | экран ввода кода из письма |
| `POST /login/waiting` | форма: `mail`, `code` | верный код → сессия и 303 на `/subscriptions` |
| `POST /login/verify` | форма: `mail`, `code` | тот же обработчик; этот адрес стоит в разметке формы |
| `POST /login/resend` | форма: `mail` | повтор письма; отказ по лимиту — с числом секунд |
| `GET /login/telegram` | — | начинает челлендж: свой `public_code` и `secret` |
| `POST /login/telegram` | — | «Войти заново» — новый челлендж |
| `POST /login/telegram/verify` | форма: `public_code`, `code` | опрос бота; успех → сессия |

**Почему два адреса на один обработчик.** `/login/verify` — адрес, который
собирает разметка (`render.py`), а `/login/waiting` — адрес самого экрана. Форма
не должна решать, куда идёт запрос, поэтому у неё свой адрес, а обработчик один.

**Отказ не ездит в адресе.** Текст отказа кладётся в одноразовую cookie и
гасится тем GET, что его показывает: иначе перезагрузка повторяла бы старый
отказ, а ссылку с чужим текстом можно было бы выдать за нашу (issue #55, #58).

### Подписки и покупка

| Метод и адрес | Принимает | Что делает |
|---|---|---|
| `GET /subscriptions` | — | подписки аккаунта: срок, состояние, кнопка скачивания |
| `GET /subscriptions/{id}/config` | — | отдаёт `.ovpn`; право решает подписка, а не запрос |
| `GET /buy` | `?days=`, `?devices=` | шаг 1–2: тариф и число устройств с ценой каждого |
| `GET /buy/confirm` | `?days=`, `?devices=` | шаг 3: сводка, итог и **право на триал** фактом |
| `GET /buy/servers` | `?days=`, `?devices=`, `?pick=…` | шаг 4: выбрать ровно столько серверов, сколько устройств |
| `GET /buy/pay` | `?days=`, `?devices=`, `?pick=…` | шаг 5: создаёт заказ, платёж и уводит на страницу оплаты |
| `GET /buy/done` | `?order_id=` | возврат с оплаты: состояние **заказа**, не перехода |
| `POST /payments/webhook/yookassa` | JSON от платёжного сервиса | подтверждение оплаты (см. §5) |

Сумма **всегда** считается `cabinet.pricing.calculate_price` и передаётся боту в
заказе; из адреса или формы она не берётся нигде. Неизвестный `days`/`devices` в
адресе подменяется умолчанием, а не роняет страницу.

### Аккаунт и способы входа

| Метод и адрес | Принимает | Что делает |
|---|---|---|
| `GET /account` | — | экран аккаунта: что привязано, что можно отвязать |
| `POST /account/link/telegram` | — | начало привязки Telegram (подтверждает бот, не браузер) |
| `POST /account/link/mail` | форма: `mail` | код на новый адрес |
| `POST /account/link/mail/confirm` | форма: `mail`, `code` | привязка по коду |
| `POST /account/unlink/telegram` | — | отвязка; последний способ входа отвязать нельзя |
| `POST /account/unlink/mail` | — | то же симметрично |

## 3. Внутренний API бота (кабинет → бот, `/internal/*`)

Один общий секрет в заголовке `X-Internal-Secret`. Наружу не выставлен: слушает
loopback. Коды ошибок — в теле (`error.code`) и в HTTP-статусе
(`account_not_found` 404, `amount_mismatch` 409, `telegram_required` 409,
`generation_failed` 502 и т. д.).

### Аккаунты

| Адрес | Принимает | Отдаёт |
|---|---|---|
| `GET /internal/accounts/by-chat-id` | `chat_id` | аккаунт или 404 |
| `GET /internal/accounts/by-mail` | `mail` | `{account: …}` или 404 |
| `GET /internal/accounts/{id}` | — | аккаунт |
| `POST /internal/accounts` | `mail`, `mail_verified_at` | созданный аккаунт |
| `POST /internal/accounts/{id}/link-telegram` | `chat_id` | аккаунт; **только в пустое место** |
| `POST /internal/accounts/{id}/link-mail` | `mail` | аккаунт; **только в пустое место** |
| `POST /internal/accounts/{id}/unlink-telegram` | — | аккаунт |
| `POST /internal/accounts/{id}/unlink-mail` | — | аккаунт |
| `GET /internal/accounts/{id}/unlink-preview` | `method` | что случится при отвязке (предупреждение до нажатия) |

### Данные аккаунта

| Адрес | Отдаёт |
|---|---|
| `GET /internal/accounts/{id}/subscriptions` | конфиги: `id`, `name`, `location`, `status`, `end_date` |
| `GET /internal/accounts/{id}/configs/{config_id}` | сам файл `.ovpn` |
| `GET /internal/accounts/{id}/balance` | бонусный баланс |
| `GET /internal/accounts/{id}/referral` | реферальный код и статистика |
| `GET /internal/accounts/{id}/trial-eligibility` | `{eligible, reason}` — `reason` машинным кодом |
| `POST /internal/accounts/{id}/promo/validate` | проверка промокода |
| `GET /internal/servers` | `{servers: [{code, name}]}` — включённые серверы |

### Заказы кабинета

| Адрес | Принимает | Отдаёт |
|---|---|---|
| `POST /internal/cabinet-orders` | `account_id`, `days`, `devices`, `servers[]`, `amount_rub` | `201 {order_id, status, amount_rub, account_id}` |
| `GET /internal/cabinet-orders/{order_id}` | — | заказ целиком: состав, сумма, статус, выданные конфиги |
| `POST /internal/cabinet-orders/{order_id}/paid` | необязательный `amount_rub` | `{status, changed}` |
| `POST /internal/cabinet-orders/{order_id}/cancel` | — | `{status}` |
| `POST /internal/cabinet-orders/{order_id}/issue` | — | `{configs[], already}` |

Заказ создаётся **до** платежа и отвергается, если у аккаунта нет `chat_id`
(код `telegram_required`): конфиги живут в `users` на `chat_id`, и выдать такому
аккаунту нечего. `changed=true` приходит только на первом подтверждении оплаты —
по нему кабинет решает, слать ли письмо. Выдача идемпотентна: повтор возвращает
`already=true` и не создаёт второй комплект.

### Сессии бота

`POST /internal/sessions/for-account`, `GET /internal/sessions/current`,
`POST /internal/sessions/revoke` — существуют и покрыты тестами, **но кабинет их
не зовёт** (см. §6, сессии).

## 4. Публичный API бота (кабинет → бот, вход по Telegram)

Отдельный сервис, отдельный адрес и **без общего секрета**: это тот же API, что
у Android-клиента.

| Адрес | Принимает | Отдаёт |
|---|---|---|
| `POST /api/v1/auth/link` | `public_code`, `secret_hash`, `mode?` | `deep_link` для бота; секрет хранится ботом хешем |
| `POST /api/v1/auth/poll` | `public_code`, `secret`, `device_nonce` | `pending` / `denied` / `session_token` + `account_id`, а в режиме привязки — только `chat_id` |

**Два режима одного флоу** (issue #65). `mode=login` (по умолчанию) — вход: бот
находит или заводит аккаунт для подтверждённого `chat_id` и отдаёт сессию.
`mode=link` — **привязка Telegram к аккаунту кабинета**: аккаунт не создаётся
вовсе (иначе свежий Telegram занял бы новым аккаунтом то самое место, которое
кабинет собирается заполнить), сессия не выдаётся, а в ответе приходит только
подтверждённый `chat_id` — его кабинет и привязывает, в пустое место. Подробности
— в [контракте §5.1](2026-10-17-backend-contract.md).

**Направление доверия.** `chat_id` появляется у кабинета **только** из ответа
бота, который проверил человека в Telegram. Кабинет не принимает `chat_id` ни из
формы, ни из адреса — иначе он привязывал бы то, что заявил браузер (тот самый
класс ошибок, что CVE-2026-53516 и nOAuth).

Состояние челленджа (`public_code` + `secret`) живёт в памяти процесса кабинета
и не переживает перезапуск — и не должно: срок челленджа задаёт бот. В разметку
уходит только `public_code`; `secret` не попадает ни в страницу, ни в лог.

## 5. Платёжный контур

```
кабинет /buy/pay
   │ 1. создаёт заказ (сумма из pricing)
   ▼
бот /internal/cabinet-orders ──▶ cabinet_orders (status=pending)
   │ 2. кабинет создаёт платёж в ЮKassa
   │    Idempotence-Key = order_id, metadata.order_id, БЕЗ receipt
   ▼
ЮKassa ──▶ страница оплаты (303 из /buy/pay)
   │ 3. человек платит
   ▼
ЮKassa ──уведомление──▶ платёжный сервис БОТА
   │ 4. бот опознаёт кабинетный платёж (order_id есть, chat_id нет)
   │    и пересылает уведомление КАК ЕСТЬ
   ▼
кабинет /payments/webhook/yookassa
   │ 5. перезапрос платежа у ЮKassa → статус succeeded + сумма + metadata.order_id
   │ 6. отметка оплаты (идемпотентно) → при changed=true:
   │      выдача конфигов ботом + письмо с вложением
   ▼
человек: письмо с .ovpn и конфиги в подписках
```

**Что чем доказывается.** Уведомления ЮKassa **не подписаны** — подписи у
современного API нет. Поэтому:

- **доказательство** — перезапрос платежа у провайдера: кабинет берёт заказ из
  `metadata` **ответа ЮKassa**, а не из тела уведомления. Связь «платёж ↔ заказ»
  ставит только кабинет, и подделать её нельзя;
- **фильтр** — сверка адреса источника с сетями ЮKassa. Несовпадение не отказ:
  список стареет, и отказ по устаревшему списку стоил бы настоящих покупок;
- **идемпотентность** — по заказу, на трёх уровнях: повтор уведомления, повтор
  выдачи и повтор письма. Отметка оплаты отвечает `changed`, и письмо уходит
  только при `true`.

**Коды ответа — часть договора:** 200 там, где повтор не поможет (чужое событие,
уже отмечено, сумма не сошлась, заказа нет), и 503 там, где повтор нужен (не
дозвонились до ЮKassa или до бота). 200 в последнем случае «съел» бы оплату.

**Публичная дверь вебхука закрыта:** в nginx на `/payments/*` стоит запрет,
бот ходит на кабинет по loopback. Если адрес кабинета зарегистрируют в панели
ЮKassa, запрет придётся снять — это помечено в самом конфиге.

## 6. Где какие данные живут

### В базе бота (кабинету недоступна напрямую)

| Таблица | Что в ней |
|---|---|
| `accounts` | аккаунт: `mail`, `mail_verified_at`, `chat_id`. Канонический ключ человека в кабинете — `account_id` |
| `users` | подписки и конфиги **на `chat_id`**: имя профиля, срок, регион |
| `cabinet_orders` | заказы кабинета: `account_id`, `chat_id` (снимок), срок, устройства, серверы, сумма, статус, выданные конфиги |
| `servers` | серверы: `code`, `name`, включённость |
| `pending_payments` | платежи **бота** (не кабинета) |
| `client_sessions` | сессии Android-клиента и бота |

### В памяти процесса кабинета

| Что | Срок | Почему так |
|---|---|---|
| коды входа по почте (`AuthMail`) | минуты | хранится `sha256`, не сам код; переживать перезапуск незачем |
| адрес незавершённой привязки (`pending_mail`) | пока жив код | чтобы шаг ввода кода не терялся при возврате из почтового клиента |
| челлендж Telegram-входа | срок задаёт бот | секрет не должен попасть ни в страницу, ни в лог |
| **сессии кабинета** | 180 дней, **но см. ниже** | `SingleSessionStore` |

**Сессии кабинета живут в памяти процесса, и это ограничение, а не решение на
месте.** Свой TTL — 180 дней со скользящим продлением, cookie — постоянная, но
хранилище не переживает перезапуск: **любая выкладка или перезапуск сервиса
разлогинивает всех**. Класс `SingleSessionStore` написан как временный (в его
документации сказано, что домом сессий должна стать таблица бота), а ручки
`/internal/sessions/*` у бота для этого уже есть — но кабинет их **не зовёт**.
Пока это так, «вход надолго» верно только между перезапусками.

## 7. Экраны и переходы

```
/login ──почта: код из письма──┐
   │                           ├──▶ /subscriptions ──▶ /subscriptions/{id}/config
   └──Telegram: код из бота─────┘         │
                                          ├──▶ /account ── привязка/отвязка
                                          │
                                          └──▶ /buy (тариф + устройства)
                                                   │
                                                   ▼
                                          /buy/confirm (сводка + триал)
                                                   │
                                                   ▼
                                          /buy/servers (ровно N серверов)
                                                   │
                                                   ▼
                                             /buy/pay ──303──▶ страница ЮKassa
                                                   ▲
                                                   │ возврат
                                             /buy/done (состояние заказа)
```

**Принципы, общие для всех экранов:**

- **шаг адресуем**: выбор выражается в адресе (`?days=&devices=&pick=`), поэтому
  возврат назад, перезагрузка и закладка дают то же состояние;
- **работает без JavaScript**: все переходы — ссылки, все действия — формы;
  скрипт только оживляет уже работающее (отсчёт лимита, фильтр цифр);
- **цена — только из калькулятора** `cabinet.pricing`; на экране нет ни одного
  числа, вписанного руками;
- **состояния не смешиваются**: «нет данных» и «сервис не отвечает» — разные
  экраны; «не положено» и «не проверили» — тоже (триал);
- **зелёный — только подтверждённая защита**: цена, скидка, выбор сервера не
  красятся зелёным;
- **обещание = факт**: если кабинет чего-то не умеет (письмо до подтверждения
  оплаты, право на триал до проверки), он этого не обещает.

## 8. Правила, которые нельзя нарушать

**Связывание способов входа** (тема самая опасная в проекте):

- `chat_id` присваивается **только** после подтверждения в Telegram;
- `mail` не существует без `mail_verified_at`;
- привязка — только в **пустое** место (`WHERE … AND chat_id IS NULL`); занятое
  значение никогда не перезаписывается;
- **отвязка последнего способа входа запрещена** — и запрет стоит на сервере, а
  не в разметке: POST можно отправить и без кнопки.

**Деньги:** сумма не берётся из запроса браузера нигде; основание выдачи —
подтверждение, проверенное у провайдера; повтор не создаёт второго комплекта,
второго письма и второй отметки.

**Публичность:** в репозиторий не попадают адреса серверов, домены, ключи,
секреты, содержимое `.ovpn` и данные клиентов. Адреса бота, кабинета и почты —
параметры развёртывания; в коде и тестах только зарезервированные значения.

## 9. Известные ограничения (по состоянию на дату)

1. **Сессии кабинета не переживают перезапуск** (§6) — при том что задуманы
   долгими.
2. **Продажа возможна только аккаунту с привязанным Telegram**: конфиги живут на
   `chat_id`, хранилища подписок на `account_id` нет. Кабинет даёт другое место
   покупки и другую доставку, а не другой круг покупателей.
3. **Живой платёж не пройден**: тестового режима у магазина ЮKassa нет, поэтому
   вся цепочка проверена по частям (создание платежа, пересылка уведомления,
   проверка у провайдера, выдача, письмо), но не одним настоящим платежом.
4. **Чек**: кабинет блока `receipt` не передаёт (решение владельца — чеком
   занимается страница оплаты). Попадёт ли чек покупателю — не проверено: поле
   контакта на странице рисует JavaScript, в отдаваемом HTML его нет.
5. **Триал**: право проверяется и показывается, но самого оформления триала в
   кабинете ещё нет.
